## Context

DBFS v2 is a **per-file** DAG. It can answer "what is this file at revision R."
It has **no object** that means "this project at revision R" — no commit, no
tree, no snapshot. Nothing in the prototype claims otherwise; its own tests say
so explicitly ("Per-file DAG tests only; no assumptions about a future project
DAG schema").

That is the next layer, and it is *not* designed. This ADR exists so the gap is
recorded rather than discovered later, and so nobody mistakes the per-file
substrate (ADR-035–041) for the whole system. Snapshots, undo, "which repository
state did this run against," and offline/divergent editing all want a
project-level revision, and none of them can be finished without it.

This is the layer that glues per-file DAGs together so "the repo" is a thing.

## What is genuinely open

This is Exploratory; the questions below are the decision space, not a decision.

1. **What is a project revision?** A **manifest of head ids** — an explicit
   `(file_id → revision_id, existence)` map stored as a commit-like object — or a
   **frontier / vector** across the independent per-file DAGs, where a project
   state is *derived* rather than stored. The first is git-shaped and explicit;
   the second is compacter and makes "what did this snapshot contain?" a
   computation.
2. **Project branches.** v2 branches are per-file (`main` per node). A repo-wide
   branch is a **set of per-file branches, co-versioned**, and that set has no
   name today. Is a project branch a first-class object, or a label over a
   per-file-branch mapping?
3. **Existence is versioned, not just content.** `file_nodes` carry `deleted_at`,
   and rename keeps identity (same id, new path). So a project node must snapshot
   the **file set** — creates, tombstones, renames — not just a path→revision map.
   A rename in particular is a pair of facts (identity moved, path changed) that
   a content map cannot express.
4. **There is no global clock.** The per-file DAGs are independent, so "the
   project at time T" is not readable off a timestamp; it has to be *defined*.
   That is the core reason this layer is not a thin wrapper.
5. **What does a project merge recurse into?** Reconciling two project states is
   at least two problems: reconcile the *file set* (which paths exist), then run
   each path's own per-file merge (ADR-036) for the paths that exist on both
   sides. The first has no mechanism yet.

## Why it matters beyond tidy bookkeeping

- **Offline editing.** "Very diverged → branch and try merging" needs to name and
  reconcile a whole offline **workspace**, not one file. The offline story and
  the project-DAG gap are the same missing piece.
- **Snapshots and undo.** `INSERT … SELECT` and `deleted_at` were v1's cheap
  snapshot story; at project scope they need a project revision to be cheap
  against.
- **Provenance.** "This run happened against project revision R" is unanswerable
  today.

```d2
# A project revision is a manifest over independent per-file DAGs (one option).
direction: right

proj: "project revision R\n(manifest)" {
  direction: down
  f1: "/a.rb → rev 12"
  f2: "/b.rb → rev 4"
  f3: "/c/ → folder"
  f4: "/d.rb → tombstoned"
}

da: "per-file DAG: /a.rb"
db: "per-file DAG: /b.rb"
dc: "per-file DAG: /c/"

proj.f1 -> da: "resolves into"
proj.f2 -> db
proj.f3 -> dc

proj -> next: "project merge"
next: "reconcile file set,\nthen per-file merge"
```

## Consequences

**Leaving it unspecified**

- Per-file work (ADR-035–041) is not blocked and remains useful on its own.
- Offline/divergent editing and project-scoped snapshots stay unfinished until
  this is designed.
- A future reader cannot mistake the per-file ADRs for the whole story, because
  this one is linked from the parent.

**When it is specified**

- The parent ADR (ADR-034) should gain a decision link, this ADR should be
  rewritten from Exploratory to Proposed/Accepted, and ADR-041's "TP2 not
  required" may need revisiting if project merges ever transform without the
  server lock.

## What it has to carry

A project revision is a statement about the whole workspace, so at minimum it
pins **four** kinds of fact, and three of them are not content:

| fact | why a path→revision map is not enough |
|---|---|
| content | which revision of each file |
| existence | creates and tombstones — a file present in one state and absent in the other |
| identity | rename keeps the node id and changes the path, so "the same file moved" is a fact no content map can express |
| branch | a per-file branch set, co-versioned, or the project state is ambiguous |

The fourth is the sharpest: v2 branches are **per file** (`main` per node). A
repo-wide branch is a *set* of per-file branches, and that set has no name today.
Without it, "check out `feature`" has nothing to resolve against.

```d2
# A per-file DAG answers "this file at R". A project revision must answer "this
# workspace at R" — which is a statement about the file set too, not just content.
direction: right

pf: "per-file DAGs (independent)" {
  direction: down
  a: "/a.rb  rev 3 -> 7"
  b: "/b.rb  rev 1 -> 4"
  c: "/c/    folder"
}

proj: "project revision R" {
  direction: down
  m: "manifest: (file_id -> revision_id)"
  e: "existence: created / tombstoned"
  r: "renames: identity moved, path changed"
  br: "branch set: which per-file branch"
}

pf.a -> proj.m
pf.b -> proj.m
pf.c -> proj.m
```

## Two shapes, neither chosen

1. **Explicit manifest** — a commit-like object holding
   `(file_id → revision_id, existence)`. Git-shaped, and a project revision is a
   real row you can point at, label, and diff. The cost is that every write
   potentially dirties a project-level object.
2. **Derived frontier** — a project state is *implied* by a frontier (a set of
   per-file heads), and "what did this snapshot contain" is a computation rather
   than a stored fact. Compacter, and it makes the state a consequence of the
   per-file DAGs rather than a second source of truth. The cost is that a state
   you cannot compute is a state you cannot name.

The second is attractive precisely because it avoids a second authority — the
same reason v1's ADRs kept `DirectoryEntry` as the single row per path. The first
is attractive because "which revision did this run against" wants to be a stored
fact, not a derivation that must still be computable later.

## Why it is not a thin wrapper

Three of the four facts above live in *different* places: content in the revision
DAG, existence in `deleted_at`, identity in the node id. And the per-file DAGs are
independent — there is no shared clock, so "the project at time T" is not readable
off a timestamp. It has to be **defined**, and defining it is the decision.

A project merge is likewise two problems, not one: reconcile the *file set* (which
paths exist on both sides, which were added, which deleted), then run each shared
path's own per-file merge (ADR-036). The first has no mechanism at all yet.

## Open questions

1. **Manifest vs frontier** (above).
2. **Project branches** — first-class object, or a label over a per-file-branch
   mapping? And what does "check out a branch" do to a file that does not exist
   on it?
3. **Merge base for a project** — two project states need a project-level LCA,
   which is a different computation from a per-file LCA.
4. **Snapshot cost** — v1's snapshot story was `INSERT … SELECT` plus a
   `created_at` filter. A project revision has to be comparably cheap or the
   feature will not be used.
5. **Interaction with the working area** — does materializing project revision R
   to the PVC conflict with the watcher, which is watching that same tree?
6. **Garbage collection** — if project revisions are stored, what retains them?

## Relationship to the per-file ADRs

This ADR does not weaken any of ADR-035–041; those decisions stand on their own
evidence. It records that they are the **substrate**, and that the questions above
are where the remaining work is. When this is specified, ADR-034 gains a decision
link and ADR-041's "TP2 not required" may need revisiting if project merges ever
transform without the server lock.
## Alternatives considered

- **Fold a project DAG into the per-file ADRs.** Rejected: it is a different
  problem with a different decision space; burying it would hide the gap.
- **Treat "project revision" as a timestamp over the per-file heads.** Rejected as
  a premise: the per-file DAGs are independent, so there is no single clock to
  order them by.

## Context

CARB/IDE has had a database-backed filesystem since the original CARBIDE, roughly
twelve years ago, written in a day or two so the hobby project could have
multi-user editing and a revision history *in the happy case*. DBFS v1 in
CARB/IDE2 is that same idea re-cut quickly: it stood in for a job and made the
product run. It was **not** meant to be robust, and not meant to be good. It was
a stand-in, and it is still standing in.

It is now the load-bearing filesystem, and the things the product wants next are
beyond its reach:

- **Branching and merge.** v1's history is a single linear chain per file
  (`FileChange` ordered by `revision`). A branch is not representable, and a merge
  has nothing to merge against — ADR-004's own open question has no substrate.
- **Concurrent editing without a global order.** `fs/write` appends the client's
  deltas as given, with no base revision and no transform. Convergence today is
  whatever order the server happened to apply them in.
- **History that survives an ordinary event.** A delete is `destroy!`, which
  cascades the whole log (ADR-004). A `git pull` or an atomic save destroys a
  file's history as a matter of routine.
- **Structure that survives contact with a shell.** Symlinks are skipped or
  silently followed depending on which component walked the tree (ADR-026).
- **Binaries off the PVC.** v1 keeps binary bytes on a `local-path` volume and
  only metadata in Postgres. That was free on one node; on more than one it is a
  data-loss-shaped cost.

None of this is a defect discovered late. It is the known cost of a stand-in that
outlived its intent.

## Decision

**Build DBFS v2: a per-file revision DAG with branches, OT and three-way merge,
content-addressed blobs, and tombstones — as a standalone package, spliced into
CARB/IDE2 as the model layer.**

This is not a rewrite for its own sake. It is the implementation that was
intended to replace the hobby-level one, finally specified.

Two layers, named explicitly so neither is mistaken for the whole:

1. **Per-file substrate** — a revision DAG, branches, merge, OT, blobs,
   tombstones. Specified by children ADR-035 through ADR-041.
2. **Project / repo-directory DAG** — the glue that makes "this repository at
   revision R" a single addressable thing. Still undesigned; ADR-042
   (Exploratory).

**v2 is not complete when the per-file DAG works.** Per-file history answers "what
is this file at revision R"; it cannot answer "what is this *project* at revision
R", which is what snapshots, undo, and the git-shaped mental model actually ask
for. The two layers are the point of the exercise.

### Where v2 lives

The prototype is a standalone ActiveRecord application. To splice it in it must
become a **library both processes load** against the shared Postgres schema
(worker and Rails already share it; ADR-001, and expand/contract migrations,
crabide2#17). The per-file call-site inventory — what maps to what — is recorded
in the prototype's `docs/integration-notes.md`.

### Relationship to v1's ADRs

These children **supersede by intent** ADR-001 (linear log), ADR-003
(external-write semantics), ADR-004 (deletion & identity), ADR-005 (keyframe
read model as a proposal), and ADR-026 (symlinks). They are not flipped to
`Superseded` yet: per ADR-000, supersession flips when the replacement lands, and
v2 has not shipped into CARB/IDE2. Until then the old ADRs remain the description
of the running system, and this one describes where it is going.

```d2
# The shape change: v1 is one line per file; v2 is a graph with named branches.
direction: right

v1: "v1 — linear log" {
  direction: right
  a: "rev 0 setContents"
  b: "rev 1 insert"
  c: "rev 2 insert"
  a -> b -> c
  note: "no branch, no merge,\nno base revision"
  c -> note {style.stroke-dash: 3}
}

v2: "v2 — revision DAG" {
  direction: right
  g: genesis
  e1: edit
  e2: edit
  head_main: "main head"
  head_feat: "feature head"
  m: "merge\n(2 parents)"
  g -> e1 -> e2 -> head_main
  e1 -> head_feat
  head_main -> m
  head_feat -> m
}
```

## The round trip

A single keystroke, end to end — and the three places the bytes end up.

```d2
# Vertical levels. Client / Worker / each store are VISIBLE containers;
# the invisible wrappers only group each level in a row.
direction: down

client: "Client (browser)" {
  direction: right
  mon: "MonacoEditor\nkeystroke → delta ops"
  pane: "FilePane\nfs/write { path, changes, base }"
  apply: "applyRemoteChange"
  mon -> pane
}

worker: "Worker (EventMachine)" {
  direction: right
  fs: "FsStore\nhandle_write"
  doc: "DocumentCache\nwarm buffer"
  bc: "broadcast\nfs/change"
  fl: "VfsFlusher"
  wt: "VfsWatcher\ninotify"
}

dbfs: "" {
  style: { stroke-width: 0; fill: transparent }
  direction: right
  store: "Store#write"
  lock: "branch row lock\n(FOR UPDATE)"
  xf: "transform past\nthe intervening revs"
  kf: "keyframe\n(on threshold)"
  store -> lock -> xf -> kf
}

stores: "" {
  style: { stroke-width: 0; fill: transparent }
  direction: right
  pg: "Postgres" {shape: cylinder
    direction: down
    rev: "revisions (DAG)"
    br: "branches (head)"
    kfr: "keyframes"
  }
  s3: "S3 / MinIO" {shape: cylinder
    direction: down
    blobs: "content-addressed\nblobs (archive)"
  }
  pvc: "PVC — working area" {shape: cylinder
    direction: down
    live: "text, real file IO\n(derived cache)"
  }
}

client.pane -> worker.fs: "1 fs/write"
worker.fs -> dbfs.store: "2 write"
dbfs.kf -> stores.pg: "3 append + advance head"
dbfs.kf -> stores.s3: "4 binary bytes → BlobStore"
dbfs.kf -> worker.doc: "5 advance cache"
worker.fs -> worker.bc: "6 fan out"
# drawn client->worker so the client stays the top layer; the arrowhead points
# back at the client, i.e. the worker fans the change out to it (step 7).
client.apply -> worker.bc: "7 fs/change" {source-arrowhead.shape: arrow}
worker.fl -> dbfs.store: "read current"
worker.fl -> stores.pvc: "write TEXT only"
stores.pvc -> worker.wt: "inotify"
worker.wt -> dbfs.store: "external → setContents / Ingest"
```

Top to bottom: the client, the worker, the DBFS write path, then the three
backing stores. The invisible wrappers are grouping only — they place each level
in a row. Steps 1–7 are the interactive path: a write is durable *before* it is
broadcast. The flusher/watcher pair is the separate disk-facing loop against the
PVC. Binaries leave through the `BlobStore` and never enter the text log.

## Consequences

**Positive**

- Every product goal that v1 cannot reach — branch, merge, durable history,
  symlinks, offline editing, binaries off the PVC — has a substrate.
- The per-file log becomes a DAG without losing the append-only promise: nothing
  is ever squashed or deleted (ADR-035).
- v2 already exists as a tested prototype; this is integration, not invention.

**Negative / to resolve**

- Two models coexist during the transition. Running both is debt, not a path;
  `DirectoryEntry` is repointed at `DbfsV2::Store` and retired.
- The editor wire changes: `fs/write` gains a base revision, and `revision`
  becomes an opaque id rather than `file_changes.count`.
- The client needs a JavaScript port of the transform for offline editing —
  bit-compatible with the Ruby, because the diff tie-break and fold order are
  semantic, not incidental.
- The project DAG (ADR-042) does not exist, and offline/divergent editing cannot
  be finished without it.

## Data model

The v2 entities, and what each replaces in v1:

| v2 | v1 | note |
|---|---|---|
| `FileNode` (UUID id) | `DirectoryEntry` (integer id) | the path is an *attribute* of the node; adds `deleted_at`, `symlink_target` |
| `Branch` (name, `head_revision_id`) | — | `main` auto-created per node |
| `Revision` (`parent_id`, `second_parent_id`, `change_type`, `change_data`, `priority`, UUID id) | `FileChange` (`revision = count`) | a DAG, not a chain |
| `Keyframe` | — | full-content snapshot, used *only* to skip replay |
| `Blob` (`digest` PK, `bytea`, `size`) | binary bytes on the PVC | content-addressed, behind the `BlobStore` seam |

Migrations `001..005` create these; `006` makes the `[project_id, path]` unique
index **partial** (`WHERE deleted_at IS NULL`), which is what lets a live node and
a tombstoned history coexist at one path (ADR-035; this is ADR-004's own
"partial index" resolution).

## The wire changes

`fs/write` gains a base revision. v1 sends deltas with no base:

```
-> { cs:'fs', cmd:'write', payload:{ path, changes:[ { change_type, change_data, start_line, ... } ] } }
<- { cs:'fs', cmd:'written', payload:{ path, revisions:[ 7, 8 ] } }     // == file_changes.count
```

v2 threads the base and can refuse:

```
-> { cs:'fs', cmd:'write',   payload:{ path, changes:[...], base: <revision_id> } }
<- { cs:'fs', cmd:'written', payload:{ path, revisions:[ <id>, ... ] } }   // opaque ids
<- { cs:'fs', cmd:'conflict',payload:{ path, base, head } }                // new frame
```

Three consequences worth stating plainly: `revision` stops being an integer the
client can compare or increment; the client must render a **conflict** state that
does not exist today; and the agent tools already carry `base_revision` (as
content-keyed CAS), so the *field* is not new even though the semantics are.

## Open questions

1. **Agent tools.** They already do content-keyed CAS + reject (`{ stale: true }`).
   Do they move onto the same transform path, or keep rejecting and let the model
   re-read? Both are correct; they differ in who retries.
2. **Mixed fleet.** During the transition the editor wire changes for everyone at
   once, or is versioned (`ADR-019` caps) so a stale client is told to reload?
3. **Cutover.** Does v2 land as a wipe-and-re-import (ADR-026's precedent for
   existing rows), or is there a migration from `FileChange` to `Revision`? A
   migration is machinery that exists only for a pre-alpha install.
4. **Where the split lands.** `DirectoryEntry` could become a thin façade over
   `Store` (smaller diff, two models live on) or be replaced outright (bigger
   diff, one model). Not decided here.

## Out of scope

- **Hardlinks.** Not modeled (ADR-026).
- **Project/repo-directory DAG.** ADR-042; explicitly not this decision.
- **A CRDT store.** Parked by ADR-001; v2 keeps the per-keystroke log.
## Alternatives considered

- **Keep v1 and add branching on top.** Rejected: v1's log is linear by
  construction. Branching needs a second parent, which is not a column you bolt
  onto `file_changes` without becoming v2.
- **Adopt git (or a CRDT store) wholesale.** Rejected for now: git is the wrong
  granularity for per-keystroke collaborative editing, and a CRDT store swaps one
  large dependency surface for another while losing the per-keystroke audit log
  that is the whole point. ADR-001 already parked CRDT as a possible overlay.
- **Patch v1 in place until it hurts more.** Rejected: the prototype shows the
  target is small and bounded; the cost of carrying v1 grows with every feature
  that assumes a DAG it does not have.

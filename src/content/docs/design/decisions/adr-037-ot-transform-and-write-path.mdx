## Context

v1's `fs/write` appends whatever the client sends. There is no base revision, so
there is nothing to transform against and no notion of a conflict — the "OT" is
an append order enforced by the server. v2 must accept a **stale base** and do
something correct with it.

Several details of the transform are **semantic, not incidental**, and have to be
pinned:

- **One coordinate space.** Every delta normalizes to primitive splices
  `(start, end, text, priority)`. Mixing chained and same-space coordinates
  compounded shifts wrongly; everything is same-space now.
- **Fold order.** A single revision can emit several prims (a multi-hunk
  `setContents` diff, a multi-match regex replace). `transform_list` folds the
  others **right-to-left** (descending start), because a prim to the right never
  shifts one to its left. List order compounded shifts in the gaps between prims
  and silently deleted the wrong text.
- **The diff tie-break.** With repeated tokens the placement of an added token is
  ambiguous (all minimal). Myers appends at the **end**; which is chosen decides
  where a concurrent edit near the repeats lands. The tie-break is a pinned
  semantic, not an optimisation — a diff swap that changes it must fail loudly.
- **Insert-inside-replace is opaque**, and that is why it cannot be split: both
  halves would need the replacement text, and an insert cannot be ordered
  unambiguously within one prim. It is routed to the conflict path, not guessed.

## Decision

**A write carries its base. The server validates against that base, transforms
the op past the intervening revisions under the branch lock, and either appends
or raises a typed `ConflictError`.**

- **Position semantics are positional OT.** A concurrent insert shifts a stale
  cursor by its length; a keystroke based at "end of world" lands after an
  inserted header, not re-anchored to the head.
- **`setContents` is diffable, not an opaque clobber.** `to_prims` diffs the new
  content against the parent, so a `setContents` means "these are my changes" and
  merges with concurrent edits. A genuine full rewrite degenerates to a replace
  over the whole range, which overlaps everything — a conflict.
- **One entry point.** `transform()` is a thin wrapper over the same prim fold
  the live path uses. The old opaque `transform_opaque` (a snapshot the
  production path never took) is gone; a pairwise call and the Store agree, and an
  ambiguous overlap raises in both.
- **Write anchors its base under the lock.** `write` captures the revision it
  validated against (caller base, or the head for a blind append) and uses that
  as the effective base, so a foreign write landing between validation and lock is
  transformed against rather than mis-applied. Validation runs against
  `Content.at(node, base)`, not a fresh head read.
- **Serialization is the branch row lock** (`SELECT … FOR UPDATE`). Every write
  and merge takes it, so there is one total order and each stale op is transformed
  along exactly one path — the Jupiter / Google-Docs model, where TP1
  (two-operation convergence) is sufficient.
- **The diff is Myers O(ND)** with common prefix/suffix trimmed and a bounded
  edit distance; past the cap a genuine rewrite falls back to one coarse hunk.

```d2
# The live write path: base in, lock, transform, append or refuse.
direction: right

c: "client\nfs/write(path, changes, base)"
v: "validate vs\nContent.at(base)"
lk: "branch row lock\n(FOR UPDATE)"
x: "transform past\nintervening revisions"
g: "ambiguous?"
ap: "append revision\n(broadcast)"
cf: "ConflictError\ncommitted nothing"

c -> v
v -> lk
lk -> x
x -> g
g -> ap: "disjoint"
g -> cf: "overlap"
```

### Decision points

The same path as a decision sequence. Only two branches change the outcome: an
overlapping write refuses, and a binary skips the transform entirely. Everything
else is bookkeeping.

```d2
# Every branch a write takes, in order. Only two of them change the outcome.
direction: down

start: "fs/write(path, changes, base)"

qbin: "binary?"
bin: "writeBinary → BlobStore\nno OT — last write wins"

qstale: "base == head?"
blind: "blind append\n(genesis makes this rare)"
current: "no transform needed"

xf: "transform past\nintervening revisions"
qov: "ambiguous?\n(overlapping writes)"
conflict: "ConflictError\nnothing committed"
apply: "append a revision"

qkf: "keyframe threshold\ncrossed?"
kf: "write keyframe\n(skip-replay hint only)"
done: "advance cache\nbroadcast to peers"

start -> qbin
qbin -> bin: "yes"
qbin -> qstale: "no"
qstale -> blind: "empty / no base"
qstale -> current: "current"
qstale -> xf: "stale"
current -> apply
blind -> apply
xf -> qov
qov -> conflict: "yes"
qov -> apply: "no"
apply -> qkf
qkf -> kf: "yes"
qkf -> done: "no"
kf -> done
```

## Consequences

**Positive**

- A stale edit is transformed and survives, instead of clobbering or being
  clobbered by whatever landed first.
- The pairwise API and production share one fold, so a property test exercises
  the code that runs.
- Conflicts are typed and fail closed — nothing is committed on refusal.

**Negative / to resolve**

- **TP2 is not tested, deliberately.** With a single serializing lock, each op is
  transformed along one path, so TP2 is not required; the transform does violate
  it (verified), and a TP2 test would send someone chasing a property this
  architecture does not need.
- The lock is a no-op on SQLite (the Arel visitor drops the clause), so the
  serialization guarantee is only real on Postgres and must be tested there.
- The client needs a bit-compatible JS port of this transform (fold order, Myers
  tie-break, conflict gate) for offline editing.

### Primitives and the one coordinate space

Every delta normalizes to a flat character-offset splice:

```ruby
(start, end, text, priority)   # insert: start == end
                               # delete: text == ""
                               # replace: decomposes to [delete, insert]
```

Two conventions existed (chained and same-space) and mixing them compounded
shifts wrongly. Everything is same-space now: `transform_di/dd/dr` emit
post-other remnants applied **right-to-left**, and `apply_transformed!` folds at
the **prim level**, with no re-encode between hops.

### Fold order is right-to-left, and it is load-bearing

A single revision can emit several prims — a multi-hunk `setContents` diff, or a
pcre replace with several matches. `transform_list` sorts `others` by
**descending start** before folding, because a prim to the *right* never shifts
one to its left, so each other stays valid in the op's current space.

Folding in list order was wrong: after the op moved past `p1` it was in post-`p1`
space, but it was then transformed against `p2`, still in *base* space, so the
shifts compounded. The bug slipped past the overlap gate whenever the op sat in
the **gaps** between prims (`ambiguous?` false, so the precise fold ran).

Observed, deterministically: a pcre `-` → `===` on `a-b-c-d`, then a stale delete
of `b`, deleted `c` — yielding `"a===b======d"` instead of `"a======c===d"`. The
index tie-break keeps equal-start prims stable.

### Insert-inside-replace never splits

There is no correct prim split for an insert inside a replace: both halves would
need the replacement text, and an insert cannot be ordered unambiguously relative
to the replacement within one prim. That is *why* it is a conflict rather than a
clever fold. The two branches that used to attempt it (both of which doubled
content) are now a `raise`, so any future narrowing of `ambiguous?` crashes
loudly instead of silently duplicating text.

### The diff: Myers, bounded, with a pinned tie-break

`diff_hunks` trims the common token prefix/suffix first (exact — any minimal edit
script keeps them), then runs `DbfsV2::Myers` on the middle only, minimal at cost
`n + m − 2·LCS`. Past `MAX_D` (a genuine full rewrite) Myers returns nil and the
caller falls back to one coarse hunk — correct, and right for that case.

The tie-break is a **semantic choice**: with repeated tokens the placement of an
added token is ambiguous and all options are minimal. `"a\na"` → `"a\na\na"` can
insert the extra `a` first, second or third, and *which* decides where a
concurrent edit near the repeats lands. It is pinned: Myers appends at the END,
`[[2, 2, 2, 3]]`. A future diff swap that changes this changes OT position
semantics and must fail that test loudly.

History is unaffected either way: replaying a `setContents` sets stored content
and never runs the diff.

### Write anchoring

`write` captures the revision the edit is validated against and uses **that** as
the effective base under the lock:

- caller base, or the head for a blind append;
- validation runs against `Content.at(node, base)` — the revision the edit is
  anchored to — not a fresh head read.

A foreign write landing between validation and lock is therefore *transformed
against*, not mis-applied. `Chain` reloads its associations so a foreign-written
revision is visible, and `DocumentCache.advance` takes the revision's `parent_id`
and **drops** the entry when the cached head is not that parent (a `nil` cached
head does not survive: `nil != parent` invalidates it), which is what fixes
keyframe drift under a cross-process write.

### `transform()` is a wrapper, not a second implementation

The pairwise entry point used to route opaque ops and ambiguous overlaps to a
`setContents` snapshot — which is *not* what the live path or merge do (they
expand pcre into splices and raise on overlap). The two disagreed. It is now a
thin wrapper over the same fold:

```ruby
def transform(a, b, base)
  a_prims = to_prims(a, buf); b_prims = to_prims(b, buf)
  raise ConflictError if ambiguous?(a_prims, b_prims)
  [encode(transform_list(a_prims, b_prims), ...), ...]
end
```

`transform_opaque` / `opaque?` are deleted. A raised `ConflictError` counts, in
the property tests, as "converged by both refusing".

### Cache advance sits outside the transaction

`append!` defers `advance_cache!` via `ActiveRecord.after_all_transactions_commit`,
so a rollback cannot leave in-memory state advanced. `write` validates (including
compiling a pcre pattern) **before** the transaction, so a bad delta fails closed
without poisoning the file.

## Open questions

1. **Runtime policy for serialization.** The lock is Postgres-only in practice
   (SQLite drops the clause). Enforcing it needs a Postgres CI run, not a skip.
2. **Binary is not OT.** Two concurrent `write_blob`s are last-write-wins.
3. **PCRE budget.** `Settings#regexp_timeout` bounds a match; it is
   process-global and per *match* (ADR-040).
4. **Coalescing keystrokes.** A merge of same-user adjacent inserts would cut row
   count while retaining the edit; explicitly *not* erasure. Not built.
## Alternatives considered

- **Append order with no transform (v1).** Rejected: it cannot express a stale
  base, so it cannot distinguish "a concurrent edit" from "a clobber."
- **CRDT merge semantics.** Parked (ADR-001): a much larger dependency surface,
  and it does not give the per-keystroke audit log for free.
- **Opaque `setContents` on any overlap.** Rejected: it silently relocates a
  stale edit and discards the other writer's intent.

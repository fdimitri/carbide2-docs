## Context

v1 keeps binary bytes on the workspace PVC and tracks only stat/mtime in
Postgres. That was deliberate and free on one node; the moment there was
somewhere else to schedule it stopped being free — a pod that reschedules leaves
its binary files behind, while text returns because text really is in the
database.

Two further v1 properties are worth separating: binary content has **no
`FileChange`**, and binary "merging" is last-write-wins, not OT.

## Decision

**Binary bytes live in a content-addressed byte store behind a `BlobStore` seam,
addressed statelessly by version. The PVC remains the live working area; the byte
store is the archive.**

- **`BlobStore` is an interface, not a choice.** `put(bytes) → sha256`,
  `get(digest)`, `exist?` / `size` / `delete`, optional native `read_range`. A
  `DbBlobStore` (Postgres `bytea`) is the default; object storage (MinIO/S3) or a
  distributed FS (Ceph) satisfies the same interface. **Content addressing is
  what makes a swap safe**: a digest names exact bytes, so any backend returning
  those bytes for that key is correct, and a digest-keyed cache can never be
  stale.
- **Blob IO is stateless and version-addressed.** Every op is a pure function of
  `(path, revision, offset)`. The server holds **no file descriptor**; an fd is a
  mutable cursor that hides the version, is not durable server state, and would be
  a second coordinate system alongside text's revision bases. POSIX ergonomics
  come from a client-side cursor pinned to a revision.
- **Binary is last-write-wins, not OT.** Two concurrent `write_blob`s do not
  merge; they are a conflict the caller resolves. A binary file still flows
  through the same per-file DAG (branches, revisions, reconstruction).
- **One ingest function, two triggers.** `Ingest` is the only path that commits
  binary content: a DBFS binary write stages a temp file, renames it into place,
  then calls ingest inline; an external write arrives through the watcher and
  calls the *same* function. Ingest is idempotent by digest against the branch
  head.
- **A size cap is enforced at every byte entry point**, before storing, aborting
  the streaming copy the moment the limit is crossed. A size overrun is a typed
  `TooLargeError`, not a conflict.
- **Ordering: PUT the object, then commit the revision.** Orphans are harmless; a
  revision pointing at missing bytes is not.

## Where the bytes live

Three tiers with three jobs. Postgres holds history; the PVC holds the live copy
in-pod tools read; the object store holds bytes by digest. None of them is "the
filesystem" on its own.

```d2
# Three tiers, three jobs. History is not on disk; the disk is not the archive.
direction: down

edit: "a write"
pg: "Postgres\nrevisions DAG · branches · keyframes\nblob index by sha256 (bytea by default)" {shape: cylinder}
pvc: "PVC — working area\nthe live copy shell tools read\n(rebuilt cache, never the truth)" {shape: cylinder}
obj: "S3 / MinIO / Ceph\nbytes by digest: put once, read many\n(archive; historical content)" {shape: cylinder}

edit -> pg: "text: content + full history"
edit -> pvc: "text: flushed for in-pod tools"
edit -> obj: "binary: bytes via BlobStore seam"
pg -> obj: "revision references a digest" {style.stroke-dash: 3}
pvc -> pg: "inotify folds external writes back" {style.stroke-dash: 3}
```

## Consequences

**Positive**

- Binary bytes survive pod rescheduling — the multi-node gap closes.
- Identical bytes across revisions, branches and projects share one row.
- The byte store can be swapped for object storage without touching callers.

**Negative / to resolve**

- A Postgres `bytea` default holds the whole payload in one INSERT and carries it
  in base backups; the `BlobStore` seam exists precisely so this can move.
- Mutations (`append`/`insert`/`overwrite`/`truncate`) are read-modify-write and
  O(size); efficient append at scale wants content-defined chunking, deferred.
- `fs/blob` / `download` currently `send_file` from disk and must read the byte
  store instead.

### The seam

```ruby
# DbfsV2::BlobStore — an interface, not a choice
put(bytes)        -> sha256          # content-addressed
get(digest)       -> bytes
exist? / size / delete(digest)
read_range(digest, offset, length)   # optional native range; default slices get
```

`DbfsV2.blob_store` / `DbfsV2.with_blob_store(store)` swap the backend. Every
caller (`Blob.store`, `Content#blob_content`, `BlobIO`) goes through `put`/`get`
by digest, so nothing above the seam changes.

| implementation | backend | status |
|---|---|---|
| `DbBlobStore` | `blobs.content` (`bytea`) | **default** — transactional with the revision, no orphan window |
| `MemoryBlobStore` | in-memory | tests; proves the swap |
| `S3BlobStore` | MinIO / S3 | drop-in, same interface |
| `CephBlobStore` | CephFS (POSIX) | out of scope for the prototype; satisfiable by the same interface |

Two families qualify and differ only in *access shape*, not capability: an
**object API** (MinIO already in the cluster, S3, Ceph RGW — immutable
put-once-read-many, which matches this access pattern directly) or a
**distributed FS** (Ceph/CephFS — POSIX, which additionally gives the mirror
direct file access, at the cost of running a distributed FS).

**Content addressing is the property that makes the swap safe:** a digest names
exact bytes, so any backend returning those bytes for that key is correct, and a
digest-keyed cache can never be *stale* — eviction is size/time, correctness is
free.

### Blob IO surface

`DbfsV2::BlobIO` (stateless): `read` (range), `size`, `digest`, `create`,
`write`, `put`, `append`, `insert`, `overwrite`, `truncate`, `copy`. Every op is
a pure function of `(path, revision, offset)`. Write ops uniformly return the
**digest**.

`Store#blob_cursor` / `DbfsV2::BlobCursor` gives POSIX ergonomics *client-side*:
a cursor pinned to one revision, with `seek(:set/:cur/:end)`, `read`, `read_all`,
`tell`, `eof?`, `close`. The server holds no fd.

### Layers, kept distinct

| | what it is | mutable? | who writes it |
|---|---|---|---|
| **working area (PVC)** | the live copy shell tools read | yes, in place | the flusher (text), inline ingest (binary) |
| **archive (byte store)** | historical revision content | no, digest-keyed | ingest / `write_blob` |

inotify applies **only** to the working area. The byte store is read by digest and
never watched, so the archive tier's layout is independent of inotify's limits —
which is what makes "Ceph as the byte store" a swap that does not touch the live
file.

### Ingest

One function, two triggers:

- **DBFS binary write (incl. upload)** — write a temp file on the PVC, rename it
  into place, call ingest **inline** (not via inotify). The trailing watcher event
  is a no-op by digest.
- **External write** — inotify → watcher → the *same* ingest.

Steps: hash while copying into a local cache file → rename the cache file to its
digest **after** the clean-read check → upload to the byte store → commit the
revision. The read is guarded: the inotify watch is held, and any `IN_MODIFY` /
`IN_CLOSE_WRITE` / move for that path during the read **discards** the read and
reruns. **Losing an intermediate state overwritten mid-read is accepted**;
`fstat` before/after and double-read-until-stable were considered and rejected as
the mechanism. `IN_Q_OVERFLOW` marks the tree dirty and rescans.

The cache dir is local, digest-named, and **outside the watched tree** — so it
cannot be re-ingested, and a torn read never reaches it (rename-to-digest happens
only after the clean-read check).

Ingest is **idempotent by digest** against the branch head. That has a useful
consequence: revision inspection never writes the working tree, so there is no
materialize-vs-commit split; materializing a branch resolves to `(file, branch)`
and is a no-op by the same rule.

For a *new* path the genesis **is** the content — `Ingest` takes
`create_if_missing:` and creates the node with the staged content, one revision,
rather than an empty-binary genesis followed by the content.

## Open questions

1. **Where the bytes live long-term.** `bytea` binds the whole payload in one
   INSERT and carries it in base backups. The hybrid (inline below a threshold,
   object storage above) is a small schema change, not built.
2. **Efficient append.** `append`/`insert`/`overwrite`/`truncate` are
   read-modify-write and O(size). Content-defined chunking (a blob is a list of
   chunk digests; append keeps the prefix) is the fix if it is needed.
3. **Binary merge.** Two `write_blob`s conflict rather than merge; whether the UI
   offers LWW or a pick is open.
4. **`mmap`'d writes** are undetected; project policy excludes them.
## Alternatives considered

- **Keep bytes on the PVC (v1).** Rejected: it is a data-loss-shaped cost the day
  there is a second node.
- **Server-side file descriptors for seek.** Rejected: not durable, not
  versionable, and a second coordinate system that must be reconciled with
  concurrent edits.
- **Inline everything in `bytea` with no seam.** Rejected: the seam costs one
  interface and buys the ability to move without a migration of callers.

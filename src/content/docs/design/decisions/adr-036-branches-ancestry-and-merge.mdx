## Context

v1 has no branches and no merge. A branch is a named pointer at a head revision
(`main` auto-created); a merge is any of fast-forward, a three-way merge, or a
human resolution.

Two walks over the same graph, deliberately different:

- **Ancestry membership** (is A an ancestor of B? is this a fast-forward? what is
  the merge base?) needs the **full DAG**, both parents.
- **Replay** (what are this revision's bytes?) needs the **first parent only**,
  because a merge commit is a full-content snapshot and its content is fully
  determined by the first-parent line.

## Decision

**Ancestry is a full-DAG walk; replay is a first-parent walk. Auto-merge is a
three-way merge at the DAG base, and overlapping *writes* are a surfaced
conflict — never a silent pick.**

- **Ancestry (`reachable_ids`)** descends both parents, cycle-guarded, and backs
  `fast_forward?` and `lowest_common_ancestor`. A merge commit's second parent is
  an ancestor of it, so a branch already merged in can fast-forward onto it.
- **Replay (`ancestor_ids`)** is first-parent, ordered genesis → head. When a
  caller's `since` / base is not on that line, `new_since` / `revisions_between`
  return `found: false` and the caller replays from scratch rather than
  transforming against the wrong chain.
- **Fast-forward** moves the branch pointer, re-checked **under the target's row
  lock** so a concurrent write is not orphaned.
- **Auto-merge is a real three-way merge at the merge base**: diff the base
  against each head into prims (both in base coordinates), OT-transform the
  source's prims past the target's, apply both. Merging a branch twice does not
  replay already-merged edits, because the base is the previous source head.
- **The conflict gate is diff-based and shared.** `merge_conflicts?` and
  `merge_auto` make the *same* check against the merge base and cannot disagree.
  Overlapping **insert/delete** overlaps auto-merge (both edits survive; priority
  is a legitimate tie-break). Two concurrent ops that **replace/write** the same
  region are a conflict for a human — no content-hash priority may pick between
  two people's rewrites.
- **A user-resolved merge pins both heads.** `expected_head` (target) and
  `expected_source_head` (source) are required; the pinned source revision is what
  is recorded as `second_parent`. If either advanced since the human resolved,
  `ConflictError` — re-resolve, do not record a merge that skipped a write.
- **A merge is its own change type** (`mergeAuto` / `mergeResolved`) carrying the
  params, not a bare `setContents`. `mergeResolved` always stores the human's
  bytes (that is the decision, not derivable); `mergeAuto` stores its result too
  for now, with an `algorithm_version` recorded, so re-derivation is possible
  later without a version registry today.

```d2

```

## Consequences

**Positive**

- Branch, fast-forward, auto-merge and human resolution all exist, on one
  substrate.
- Conflict detection cannot disagree with auto-merge — they share the check.
- The merge node is labelled in the log, so "how did this fork join" is
  answerable.

**Negative / to resolve**

- `lowest_common_ancestor` picks one base deterministically when criss-cross
  histories admit more than one; a fixture should pin that choice and that
  `merge_auto` / `merge_conflicts?` agree with it.
- Storing `mergeAuto`'s output is a for-now convenience; the intent is to derive
  it from params + `algorithm_version` once that machinery exists.
- Per-file branches are not project branches — a repo-wide branch is a set of
  per-file branches, which ADR-042 has to define.

### The two walks, named

```ruby
Chain.reachable_ids   # full DAG: parent_id + second_parent_id, cycle-guarded.
                      # backs Merge.ancestors, fast_forward?, lowest_common_ancestor
Chain.ancestor_ids    # first-parent only, ordered genesis -> rev. THE REPLAY ORDER.
```

They are deliberately different. `reachable_ids` is what makes `fast_forward?`
correct *after* a merge: a merge commit's second parent is an ancestor of it, so
a branch already merged in can fast-forward onto the merge commit. `ancestor_ids`
is replay, because a merge commit is a full-content snapshot — its content is
determined by the first-parent line, and replay must not descend the second
parent.

`Store#new_since` / `revisions_between` use the first-parent chain. When the
caller's `since` is not on that line they return `found: false` / `nil`,
signalling "replay from scratch" rather than transforming against the wrong chain.

### The merge record

A merge is its own change type, so the *operation* is in the log rather than
being flattened into a `setContents`:

```jsonc
// mergeAuto — result is derivable from the params + algorithm version
{ "data": "...", "target": "main", "source": "feature",
  "target_head": "<id>", "source_head": "<id>", "algorithm_version": 1 }

// mergeResolved — the human's bytes ARE the decision, not derivable
{ "data": "...", "target": "main", "source": "feature",
  "target_head": "<id>", "source_head": "<id>" }
```

`Delta` treats both as full-content and `Transform.to_prims` diffs them against
the base exactly like `setContents`, so replay, concurrent folding and merge are
unchanged. `Merge::ALGORITHM_VERSION = 1` is recorded but not yet *used* for
derivation. The appendix the params buy: "how did this fork join" is answerable,
and a graph/audit can label the node instead of printing `setContents`.

### Head re-checks (the race that matters)

Content is computed against a head read *before* the commit lock. If a write
lands on the target in between, committing would clobber it. Every merge path
therefore re-checks under the lock:

- **fast-forward** — re-checked against the target's row lock.
- **merge_auto** — compares `locked.head_revision_id` to the head the content was
  computed from; on mismatch, aborts with
  `reason: 'target advanced concurrently; re-check'`.
- **merge_commit!** (user-resolved) — takes `expected_target_head` *and*
  `expected_source_head`; the **pinned** source revision is what is recorded as
  `second_parent`, not the source branch's current head. A source that advanced
  is not silently ignored: the pin is validated (belongs to this file, reachable
  from the source's current head) and a foreign or non-ancestor pin is a
  `ConflictError`.

`merge_auto` rescues **only** `ConflictError`. It used to rescue `StandardError`,
which reported any internal bug as `reason: 'conflict'` — a real conflict and a
`NoMethodError` must not look alike to the caller.

## Open questions

1. **Re-derive merge content.** Storing `mergeAuto`'s output is a for-now
   convenience; the intent once spliced in is to store the params + version and
   compute the bytes. That needs the whole cone versioned
   (`auto_merge_content → transform_list → diff_prims → ambiguous?`), a registry
   that can run every past version, two-parent replay, and a `result_sha256`
   tripwire. Not built.
2. **Criss-cross bases.** `lowest_common_ancestor` can have more than one valid
   merge base. It returns the first along a's reachable set — deterministic, but
   not *pinned* by a fixture yet.
3. **Binary merges.** Two `write_blob`s are last-write-wins; `merge(resolved:)`
   on a binary node is unexercised.
4. **Per-file vs project branches.** A repo-wide branch is a set of per-file
   branches; that set has no name (ADR-042).

## Out of scope

- **In-thread DAG merges for agent conversations** — that is ADR-032's scoping,
  not filesystem merge.
## Alternatives considered

- **A content-hash priority as the final arbiter.** Rejected: it is a stable
  total order for convergence, not a statement about intent. It may tie-break
  overlapping inserts; it may not choose between two rewrites of the same
  function.
- **Chain-flatten rebase for auto-merge.** Rejected (superseded in-prototype): it
  could reorder same-offset sequential edits. A real three-way merge at the base
  is correct, not merely convergent.
- **Blind second-parent tracking (no pins).** Rejected: a long human-resolution
  window makes the recorded parents stale and silently drops a concurrent write.

## Context

A single deploy host answers three independent questions, and today one flag
(`registry.host`) is used to answer all three:

1. **Membership** — what cluster does this box belong to, and in what role?
2. **Publish** — what does this box produce for *other* boxes: build images,
   push them to a registry, or host the registry itself?
3. **Consume** — how does this box's *own* cluster obtain images: import the
   local `:dev` images into its single node's containerd, or pull immutable
   SHA tags from a registry?

Question 1 already has a home (`cluster.backend`, `cluster.role`). Question 2
has a partial home (`--publish-only`, `--external-registry`). Question 3 has
**no home at all** — it is inferred from the other two, and inferred wrongly.

The concrete failure this records: a host that runs a k3d cluster for local
development *and* serves as the build/publish host for a separate k3s cluster
sets `registry.host` to its own name. That single value flips three pull-side
code paths:

- `publish_images` stops importing `:dev` and pushes instead.
- `ControlPlane#install` pins `registry.url`, `image.repository`,
  `workspace.image`, `workspace.imageTag`, and `workspace.shellImage` into the
  helm release — pointing the k3d cluster's pods at a registry its containerd
  does not trust.
- `roll_deployments` skips the forced rollout on the assumption that helm
  already rolled the pods via a new immutable tag.

The k3d node never receives containerd registry trust
(`Node#trust_registry!` is only called on the k3s path), so the pinned
registry tags are guaranteed `ImagePullBackOff`. The host wanted to *publish*
to the registry; the code concluded it wanted to *pull from* it.

The fix is not a one-line gate. The flag vocabulary itself has no name for
"publish for others, consume locally," which is why the conflation keeps
re-breeding.

## Decision

### 1. Three questions, three blocks; consumption derived by default

The overloaded `registry:` block is split so that each block answers one
question, and every leaf is a scalar so the layered config
(`defaults.yaml` → `cluster.yaml` → `--a.b.c`) merges per key.

```yaml
node:                       # membership — what this box IS
  backend: k3d              # k3d | k3s | none
  role: none                # init | join | agent | none   (k3s only; k3d and none imply none)

images:                     # the image lifecycle — what this box DOES with images
  build: true               # docker buildx the images
  shell: true               # include carbide2-shell in the build (slow, large)
  push: false               # push SHA-tagged images to the registry (implies build)
  consume: auto             # auto | import | pull — how this box's OWN cluster gets images

registry:                   # a fact about the environment — identical on every box in a fleet
  host: ''                  # endpoint; "" means no registry is involved anywhere
  port: '5000'
  ca: ''                    # PEM the pull side trusts; derived on the serve box, optional elsewhere (see below)
  serve: false              # this box runs the registry:2 container
```

`node` is what today's `cluster.backend` / `cluster.role` say. `images` absorbs
today's top-level `build` and `shell` toggles and gains `push` and `consume`.
`registry` keeps the coordinates and gains `serve`; it loses `publish-only`,
`external`, and `container` (the container name is not a deploy decision).
`client` (build + upload the SPA to MinIO) is not an image and stays top-level.

**Why booleans, not a duties list.** A list such as `duties: [build, push]`
breaks the per-key merge: an override layer either replaces the whole list —
so a `cluster.yaml` that says `[push]` silently drops the default `build` — or
the config grows a `+push` / `-build` grammar for one key. Three booleans merge
independently and `--images.push=false` on the command line means exactly what
it says.

**Why the registry's coordinates are not a publish duty.** An earlier draft of
this ADR nested `host`/`port`/`ca` under a `publish:` block. But the box that
needs them most is a *consumer*: a k3s joiner that builds nothing and pushes
nothing still needs `host` to pull from and `ca` for containerd to trust.
Calling that `publish.ca` is the same category error this ADR exists to fix,
one level down. The registry is a fact about the deployment, the same on every
node; running it (`serve`) is the one duty that lives with it.

**The CA: one field, three cases.** There is one registry, so there is one CA —
the CA that signed the certificate the registry presents is by definition the
CA a puller must trust. Separate serve-side and consume-side fields would only
describe two registries, which this block does not.

- **On the box that serves it**, `ca` is left empty and **derived**: the
  registry's certificate is minted by mkcert, so the CA is mkcert's
  `-CAROOT/rootCA.pem` on that box's disk. Storing a copy in the YAML would be
  a second source of truth that can drift from the CA mkcert actually used.
  This is what `Images#mkcert_ca_pem` does today.
- **Distribution to consumers** is `--yaml-out` on the serve box. It emits the
  fully-resolved config, and `registry_ca_text` fills `ca` from mkcert when the
  input left it empty. The emitted file is self-contained and is what every
  other node in the fleet consumes. The CA is public material — a certificate,
  not a key — so carrying it inline costs nothing but a block scalar (and
  `normalize_pem`, because YAML folds it). `--registry.ca-file PATH` remains the
  ergonomic way to *load* one; inline PEM is the way it *travels*.
- **On a consumer**, `ca` is **optional**. A puller cannot fetch the CA from the
  registry it is about to trust, so when a private CA is in play the PEM must
  arrive out of band, and the YAML is the out-of-band channel. But a registry
  whose certificate chains to a public CA — a corporate Harbor, GHCR — needs
  nothing here; empty means "the system trust store." The reachability check
  fails loudly if that assumption is wrong, which is a better failure than
  refusing to parse a config that would have worked.

### 2. Membership

- `k3d` — single-node dev (k3s-in-Docker). `role` is `none`.
- `k3s` + `init` — first control-plane server (embedded-etcd HA).
- `k3s` + `join` — additional control-plane server.
- `k3s` + `agent` — worker node. **Not implemented**; rejected at parse until
  the agent tier exists rather than silently promoted to a full server.
- `none` — no cluster on this box (pure build / registry host).

### 3. Consumption

`images.consume` defaults to `auto`, which resolves:

- `node.backend: none` → not applicable (nothing to consume into).
- `k3d` → **import** the local `:dev` images with `k3d image import`.
- `k3s` + `init` with `registry.host` empty → **import** via containerd.
- `k3s` + `init`/`join`/`agent` with `registry.host` set → **pull** SHA tags.

The k3d row is a choice, not a law of nature. On the topology this ADR was
written for, the k3d box is the developer's machine: it builds, it serves the
registry the k3s fleet pulls from, and its own cluster can eat its own build
directly. Making it also pull from itself would require wiring the k3d node to
the registry (§5) for no benefit *on that topology*.

But `auto` is a default, not a ban. **`consume: pull` on k3d is allowed and is
the only way the pull path — SHA tags, `registries.yaml`, CA trust — can be
exercised on the single environment that exists for testing.** An earlier draft
said "consumption is never a knob"; that would have left the multi-node
consumption path untestable anywhere but production nodes. `consume: import`
on a k3s joiner is rejected (there is no single node to import into).

### 4. Validation, at parse time

- `images.push` requires `registry.host`.
- `registry.serve` requires `registry.host` (it must know what name it answers to).
- `registry.serve: true` with `registry.ca` set is a warning: the value is
  ignored in favour of mkcert's CA on this box.
- `images.consume: pull` requires `registry.host`.
- `images.consume: import` requires a single-node backend.
- `node.backend: none` with `images.build`, `images.push`, and `registry.serve`
  all false is an error: the box does nothing.
- `node.role` of `join` or `agent` requires `node.backend: k3s`.
- `node.role: agent` is rejected until implemented.
- **Any key not defined in `defaults.yaml` is an error**, named, with the file
  that carried it. `defaults.yaml` is the whole schema; a key outside it is read
  by nothing, so accepting it would silently do nothing. This is also how the
  old shape fails: `cluster.backend`, `registry.publish-only`,
  `registry.external`, top-level `build` / `shell` are unknown keys, and are
  reported as such. **There is no legacy mapping, no alias, no warning period.**
  `--publish-only` and `--external-registry` do not parse. A missing `--config`
  file is likewise an error, not an empty override.

### 5. What re-keys onto `consume`

The three pull-side sites stop reading `registry.host` and read the resolved
consumption:

- `publish_images` → push when `images.push`; **and** import `:dev` when
  consumption is `import`.
- `ControlPlane#install` → pin `registry.url` and SHA image tags into the helm
  release only when consumption is `pull`.
- `roll_deployments` → skip the forced rollout only when consumption is `pull`.

And one site gains a k3d branch: **node registry trust**. Today
`Node#trust_registry!` writes `registries.yaml` via `sudo` and restarts k3s —
the host-native path. `consume: pull` on k3d needs the equivalent: the registry
container joined to the k3d Docker network under an alias equal to
`registry.host` (so the node resolves the name to the container rather than to
its own loopback), and the CA delivered at `k3d cluster create` via
`--registry-config` plus a `--volume` mount. Without this, `consume: pull` on
k3d is exactly the `ImagePullBackOff` in the Context.

### 6. Library shape follows the config shape

`Carbide::Images` today owns two unrelated things: the image lifecycle
(`build`, `push`, `image_tags`, `image_ref`, `in_registry?`, …) and the
registry lifecycle (`ensure_registry`, `ensure_registry_cert`,
`ensure_registry_container`, `verify_registry`, `mkcert_ca_pem`, …). It also
declares every `registry.*` config key. That is the config conflation
mirrored in code.

- **`Carbide::Registry`** is extracted: host, port, `serve`, and a single `ca`
  accessor that returns mkcert's root when `serve` and the configured PEM (or
  nil, meaning system trust) otherwise; owns the cert, the container, the
  reachability check, and the `--yaml-out` CA text; declares `registry.*`.
- **`Carbide::Images`** takes a `registry:` (a `Registry` or `nil`) and does
  build / push / import only; declares `images.*`.
- **`Carbide::Node`** takes the `Registry` and asks it for the CA to trust,
  replacing the hand-threaded
  `@external_registry ? @registry_ca : @images.mkcert_ca_pem` in `deploy.rb` —
  which is this ADR's bug in one line.
- **`scripts/build.rb`** constructs a `Registry` from its flags and hands it to
  `Images`, so the two entry points describe a registry the same way.
- **`scripts/configure.rb`** emits the new blocks. Its wizard's
  `registry: local | external` question is the conflated question; it becomes
  the three it always was.

## Consequences

**Positive**

- The developer box — build, push, serve the fleet's registry, and run its own
  k3d on imported images — is a first-class configuration instead of an
  accidental fall-through that happens to break.
- The pull path is testable on k3d.
- Three shapes that are impossible today become expressible: a pure registry
  store, build + push to a registry someone else runs, and a k3d cluster that
  pulls.
- A fleet is one `cluster.yaml` with one line changed per node (`node.role`);
  the `registry:` block is copied verbatim.
- `Images` stops running a registry; `Registry` stops being a side effect of
  building images.

**Negative / to resolve**

- Every existing `cluster.yaml` must be rewritten by hand. There is no
  migration: the old keys fail at parse, by name (§4). The three
  `examples/*.yaml`, the root `cluster.yaml`, and `configure.rb`'s emitter are
  updated; anything a user kept locally is theirs to redo.
- `consume: pull` on k3d is real work (§5), not a flag flip.
- `agent` is named in the schema before it exists in the code.

## Open questions

1. **Agent tier.** Lands after this split; it touches `node.role` only.
2. **`images.shell`.** Whether the shell image is a member of the build set
   (as here) or a separate top-level toggle as today. Kept under `images`
   because it is one; open in case the slow build wants a more visible switch.

*Revised 2026-09-06. The 2026-09-02 draft used `node` / `publish` with the
registry coordinates inside `publish`, no consumption override, and a
one-release compatibility window for the old keys; all three are reversed
above, for the reasons in §1, §3, and §4.*

## Alternatives considered

- **A one-line gate: pin registry tags only when `cluster.backend == k3s`.**
  Rejected as the recorded decision (it may still be an interim patch): it
  removes the symptom but leaves consumption implicit and derived from a
  publish flag, so the same conflation returns on the next topology that is
  not exactly k3d-vs-k3s.
- **Two `cluster.yaml` files per topology.** Rejected: it works today, but the
  user having to *know* which file to feed the same host is the defect. The
  vocabulary failed, not the file count.
- **`registry.role`.** Rejected: `role` is already `node.role`, and a
  three-valued role under `registry` is the same overloaded switch renamed.
  `registry.serve` is one boolean about one fact.
- **`publish:` block holding the registry coordinates** (this ADR's first
  draft). Rejected: the coordinates and CA are consumed by non-publishers.
- **`duties: [build, push, serve]` list.** Rejected: does not survive the
  layered merge or the CLI without inventing list-edit syntax.
- **Consumption as a hard derivation with no override** (first draft's
  "never a knob"). Rejected: leaves the pull path untestable on the only test
  environment.
- **Keep `Images` owning the registry and just re-key the config.** Rejected:
  landing three clean blocks on a class that still runs a registry as a side
  effect of building images reproduces the conflation one layer down.
- **A compatibility window: map the old keys, warn, remove next release.**
  Rejected. It is code that exists to make the wrong shape keep working, which
  is the opposite of what a schema change is for; it has to encode the old
  conflation in order to translate it; and there is one deploying user with a
  handful of files. Old keys are unknown keys and fail by name.

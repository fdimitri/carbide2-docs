## Context

v1 has a linear `file_changes` log per entry, replayed in full by
`calc_current`. Three properties it lacks are load-bearing:

- **Nothing is ever squashed.** ADR-001's point is that every keystroke is
  durable; ADR-005 makes keyframes a skip-replay hint, explicitly not a deletion
  mechanism.
- **Deletion is not erasure.** ADR-004 is a bug report against `destroy!`, which
  cascades the log. It resolved the model as one row per `srcpath`, tombstoned.
- **`revision` from `count` is racy** (ADR-003): concurrent appends collide, and
  the count resets if rows are removed.

## Decision

**The per-file log is an append-only DAG. History is never squashed. A delete is
a tombstone. Identity is the node id, and a path is an attribute of it.**

- **Revisions form a DAG** with `parent_id` (first parent) and `second_parent_id`
  (non-nil iff a merge commit). Current content is derived by replay along the
  first parent; the full DAG is used for merge verdicts (ADR-036).
- **Never auto-squash.** Keyframes are full-content snapshots that let replay
  *start later*; they never replace or delete what came before. A side-log /
  WAL compaction is deferred until it is actually needed, not built now.
- **`revision` is a per-entry atomic sequence**, not `count`, with a unique
  `(directory_entry_id, revision)` index. This is the fix ADR-003 already named.
- **Delete tombstones.** `delete` sets `deleted_at` on the node and its subtree;
  revisions, branches and keyframes are untouched. `read(path, revision_id:)`
  still reconstructs any pre-delete state. `restore` clears the tombstone.
- **Recreate resurrects, never forks.** Creating a path whose node is tombstoned
  reuses the same row — same id, same DAG — so a delete/recreate cycle does not
  fork history. The unique `[project_id, path]` index becomes **partial**
  (`WHERE deleted_at IS NULL`) so a live node and a tombstoned history can share a
  path; `find_any` prefers the live row.
- **Every create writes a genesis revision**, including empty files and 0-byte
  binaries. Without it the branch head is nil and the next write is a blind
  append with no base — exactly the case (two clients on a new file) where
  transform matters most.
- **Identity is the node.** Addressing is by id; the path can move under a rename
  without disconnecting a client or forking history.

```d2
# A delete hides a node; it does not erase the DAG. Recreate rejoins it.
direction: right

live: "live node\nrevs 0..5"
gone: "external rm\n→ tombstone\n(deleted_at set)"
hidden: "find/list/tree\nhide it"
hist: "read(rev 3)\nstill reconstructs"
back: "create at same path\n→ SAME row, SAME DAG"
future: "next revision\ncontinues the lineage"

live -> gone
gone -> hidden
gone -> hist {style.stroke-dash: 3}
gone -> back
back -> future
live -> future {style.stroke-dash: 3}
```

## Consequences

**Positive**

- History survives `git pull`, atomic saves, renames and external deletes —
  the cases that silently destroyed it.
- A delete/recreate cycle reads as "one document, interrupted," not two
  unrelated files.
- The read model has an honest acceleration story (keyframes) that does not
  trade away history.

**Negative / to resolve**

- The explorer must learn about tombstones (hidden by default) and resurrection.
- Tombstones accumulate; a retention/GC policy is an **open question** and would
  be the only place history is ever discarded, so it must be explicit and opt-in.
- `deleted_at` + a partial unique index is a schema change against a live
  `[project_id, srcpath]` unique index.

### Genesis: every create writes a revision

`create_file` / `create_folder` write a **genesis revision even when empty** —
including a 0-byte binary (`touch foo.png` is a real created file).

This is not bookkeeping. Without a genesis the branch head is `nil`, so the next
write is a *blind append* with no base and no transform, and two clients editing
a new empty file get **delivery order instead of priority order** — OT silently
skipped for exactly the case where it matters most. A genesis also makes
resurrect-with-empty produce an actual empty file. The empty blob is
content-addressed, so all 0-byte binaries share one `blobs` row.

Consequence: revision counts shift by one per create. Any consumer that assumed
"a new file has zero revisions" is wrong.

### Keyframes: skip replay, never compact

A keyframe is a full-content snapshot keyed by revision. It exists so a cold read
starts replay later instead of at genesis. It does **not** replace or delete the
rows before it, and pre-keyframe revisions stay reachable.

```ruby
Settings#keyframe_revisions  # nil => no automatic keyframes
Settings#keyframe_bytes      # nil => no automatic keyframes
```

The byte threshold is measured as bytes **added since the last keyframe**
(`bytes_since_kf`), not total buffer size — otherwise a large file writes a
keyframe on every keystroke. The auto-keyframe counter lives in the in-memory
cache, so a file written but never read gets no keyframe (its first cold read
replays once). Persisting that counter is the next step if it matters.

```d2
# A keyframe is a place to start reading, not a thing that removes the history.
direction: right
g: genesis
a: rev 1
b: rev 2
k: "keyframe at rev 2\n(replay can start here)"
c: rev 3
d: "head"
g -> a -> b -> k -> c -> d
k -> g {style.stroke-dash: 3}
```

### Read-path cost, stated

`stat` does one indexed `COUNT(*)` plus a content size. Text size goes through
`Content.head_cached`: O(1) on a warm cache, one replay on a cold read. The bulk
paths (`Store#tree`, `Store#list`) do not compute size at all — they emit
`{id, name, path, type, binary, symlink, children}` — so rendering a large tree
never touches content size.

The one caveat: `revisions.count` is still one `COUNT` per `stat` call. If a bulk
"stat everything" path is ever added, cache it the way binary already caches
`last_size`. Not needed for the current one-file-at-a-time flow.

## Open questions

1. **Tombstone retention.** Tombstones accumulate. A GC pass hard-deleting them
   older than N would be the *only* place history is ever discarded, so it must
   be explicit and opt-in — not a janitor that quietly runs.
2. **Undelete UI.** `list`/`tree` can already return tombstones tagged
   `deleted: true`. Whether the explorer surfaces them is a product call.
3. **`setContents` is overloaded.** It is the VFS set-content op, *and* every
   genesis, *and* every merge commit. Whether genesis and merge deserve their own
   change types (`fileCreated`-style, per ADR-004) is recorded but not decided.
4. **Persisting the keyframe counter.** Today a never-read file gets no keyframe.

## Out of scope

- **Hardlinks** (ADR-026).
- **Auto-squash / WAL side-log.** A side log that batches raw keystrokes into a
  compacted DAG is the bounded-size option (keeping the raw log for audit) and is
  deferred until it is actually required.
- **Custom on-disk revision format** instead of the database.
## Alternatives considered

- **Hard delete, as today.** Rejected: it loses history by design (ADR-004).
- **Multiple `DirectoryEntry` rows per `srcpath`.** Rejected in ADR-004: it buys
  nothing the lifecycle events in the log do not already answer, and doubles the
  bookkeeping.
- **Squash old revisions into a keyframe.** Rejected: that is history loss, and
  history is the reason the store exists.
